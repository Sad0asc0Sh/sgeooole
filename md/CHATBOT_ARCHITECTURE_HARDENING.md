# معماری پایدار چت‌بات فروشگاه

## هدف

این سند طرح ارتقای کم‌ریسک چت‌بات فروشگاه را ثبت می‌کند. هدف، حفظ قراردادهای فعلی API و رابط کاربری در کنار افزایش تاب‌آوری، سرعت ادراکی، کیفیت پاسخ، کنترل هم‌زمانی و قابلیت مدیریت از پنل ادمین است. هیچ‌یک از مسیرهای فروش، سبد خرید، پرداخت یا تنظیمات غیرمرتبط نباید به‌واسطه این تغییرات دستخوش تغییر قرارداد شوند.

## مشکلات مشاهده‌شده

| حوزه | وضعیت پیش از اصلاح | اثر عملی |
| --- | --- | --- |
| بارگذاری ماژول‌ها | چند ماژول اصلی چت، مدل یا وابستگی مورد نیاز را import نکرده‌اند. | خطای runtime در شروع یا اولین درخواست چت. |
| تنظیمات فعال/غیرفعال | پرچم `aiConfig.enabled` در مسیر چت enforce نمی‌شود. | امکان پاسخ‌گویی هنگام غیرفعال بودن سرویس. |
| ارائه‌دهندگان | فقط یک ارائه‌دهنده فعال انتخاب می‌شود و خطای موقت به پاسخ ناموفق ختم می‌شود. | افت دسترس‌پذیری و کیفیت تجربه کاربر. |
| SSE | فشرده‌سازی، timeout طولانی، نبود heartbeat و parser کلاینتِ بدون buffer می‌توانند نمایش توکن‌ها را مختل کنند. | حس عدم پاسخ‌گویی یا از دست‌رفتن بخشی از پاسخ. |
| سهمیه | بررسی و افزایش شمارنده از هم جداست و در هم‌زمانی می‌تواند از سقف عبور کند. | مصرف کنترل‌نشده و پاسخ‌های متناقض. |
| پنل‌ها | دو نمای تنظیمات با قراردادهای متفاوت وجود دارد. | خطر overwrite تنظیمات یا نمایش اطلاعات ناهماهنگ. |

## معماری هدف

مسیر چت در چهار لایه باقی می‌ماند: رابط کاربر، API سازگار با قرارداد فعلی، لایه ارکستراسیون هوش مصنوعی، و ذخیره‌سازی MongoDB. این ساختار به‌صورت تدریجی روی کد موجود اعمال می‌شود و به صف، سرویس جدید یا تغییر زیرساخت فروشگاه وابسته نیست.

| لایه | مسئولیت پس از اصلاح | راهکار سازگاری و پایداری |
| --- | --- | --- |
| رابط فروشگاه | جلوگیری از ارسال تکراری، دریافت صحیح SSE، امکان لغو و تلاش مجدد، نمایش وضعیت سهمیه. | ادامه استفاده از `POST /api/chat/stream` و fallback به `POST /api/chat`. |
| API چت | اعتبارسنجی پیام، هویت مهمان/کاربر، سهمیه اتمیک، کنترل یک درخواست فعال برای هر گفتگو، SSE استاندارد. | قرارداد پاسخ فعلی حفظ می‌شود و eventهای جدید اختیاری هستند. |
| ارکستراتور AI | ساخت prompt، بازیابی محصول، انتخاب ارائه‌دهنده، timeout، failover و circuit breaker. | API سازگار با OpenAI حفظ و فقط رفتار داخلی مقاوم‌تر می‌شود. |
| داده و مدیریت | تاریخچه محدود، تنظیمات امن، اولویت provider و وضعیت سلامت. | فیلدهای جدید default دارند و داده‌های قبلی معتبر می‌مانند. |

> **اصل کیفیت:** فقط زمانی از ارائه‌دهنده جایگزین استفاده می‌شود که هنوز هیچ بخش از پاسخ برای کاربر stream نشده باشد. پس از شروع stream، پاسخ نیمه‌تمام با اطلاع شفاف خاتمه می‌یابد تا دو پاسخ ناهمگون ترکیب نشوند.

## راهبرد ارائه‌دهندگان

ارائه‌دهنده پیش‌فرض همچنان اولویت اول است. ارائه‌دهندگان فعال دیگر بر اساس `priority` جایگزین هستند. خطاهای شبکه، timeout، پاسخ‌های 429 و خطاهای 5xx قابل failover هستند؛ خطاهای پیکربندی یا احراز هویت قابل failover خودکار نیستند تا مشکل امنیتی پنهان نشود. پس از چند خطای متوالی، یک circuit breaker کوتاه‌مدت ارائه‌دهنده را موقتاً از چرخه خارج می‌کند. این وضعیت runtime فقط در حافظه نگه‌داری می‌شود؛ در صورت restart سرویس خودبه‌خود پاک می‌شود و مانع مدیریت دستی ادمین نیست.

## کنترل درخواست و سهمیه

هر پیام دارای `requestId` یکتا است. این شناسه برای جلوگیری از ارسال دوباره ناشی از دوبارکلیک، retry مرورگر یا واکنش‌های تکراری رابط استفاده می‌شود. برای هر هویت فقط یک درخواست فعال در آن واحد پذیرفته می‌شود. سهمیه فقط برای پیام‌هایی که پاسخ معتبر دریافت می‌کنند نهایی می‌شود؛ با این حال در طول پردازش یک reservation کوتاه‌مدت وجود دارد تا هم‌زمانی از سقف عبور نکند.

## رفتار SSE

پاسخ streaming با eventهای JSON سازگار قبلی ارسال می‌شود: `token`، `done` و `error`. eventهای جدید و اختیاری عبارت‌اند از `meta` برای شناسه پاسخ و `usage` برای همگام‌سازی سهمیه. پاسخ SSE نباید فشرده شود، باید heartbeat داشته باشد و با قطع اتصال کاربر، درخواست upstream را لغو کند. کلاینت باید با buffer خطوط ناقص را نگه دارد و قبل از دسترسی به reader وضعیت HTTP را بررسی کند.

## معیارهای پذیرش

| معیار | انتظار |
| --- | --- |
| سازگاری | endpointها و payloadهای اصلی فعلی همچنان کار کنند. |
| پایداری | غیرفعال بودن سرویس، خطای provider، timeout و قطع اتصال هیچ loading بی‌پایانی ایجاد نکنند. |
| پاسخ‌دهی | توکن نخست بلافاصله پس از دریافت upstream نمایش داده شود و SSE در reverse proxy buffer نشود. |
| کیفیت | context تاریخچه و محصول حفظ شود؛ failover فقط پیش از تولید token اجرا شود. |
| کنترل هزینه | سهمیه کاربر و سقف روزانه فروشگاه به‌صورت اتمیک کنترل شود. |
| پنل مدیریت | اولویت، فعال/غیرفعال بودن، تست اتصال و وضعیت سلامت قابل مشاهده و امن باشند. |
| رگرسیون | build فرانت و ادمین، syntax backend و تست‌های جدید چت و provider بدون خطا اجرا شوند. |

## مسیر بازگشت

تغییرات provider و تنظیمات با defaultهای سازگار انجام می‌شود. چنانچه به هر دلیل نیاز به بازگشت باشد، با نگه‌داشتن ارائه‌دهنده پیش‌فرض و غیرفعال‌کردن fallback در تنظیمات، مسیر به رفتار تک‌ارائه‌دهنده نزدیک می‌شود. هیچ migration تخریبی یا حذف داده برای این بهبود در نظر گرفته نمی‌شود.
